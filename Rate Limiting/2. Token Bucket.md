# Token Bucket Algorithm – Rate Limiting

## 1. What is Token Bucket Algorithm?

Token Bucket is a rate-limiting algorithm used to control how many incoming requests an application can accept over time.

It works using a bucket containing tokens.

Basic rules:

1. A bucket has a fixed maximum capacity.
2. Tokens are added to the bucket at a fixed rate.
3. Every incoming request must consume one token.
4. If a token is available, the request is allowed.
5. If no token is available, the request is rejected (or delayed, if the implementation supports waiting).

In simple words:

The application allows a request only when a token is available in the bucket.

## 2. Understand the configuration

Let's consider an example:

| Configuration   | Value      | Meaning                                 |
| --------------- | ---------- | --------------------------------------- |
| Bucket Capacity | 5 tokens   | Maximum tokens the bucket can hold      |
| Refill Rate     | 1 token    | One token is generated                  |
| Refill Interval | 10 seconds | One token is generated every 10 seconds |
| Request Cost    | 1 token    | Every request consumes one token        |

## 3. Step-by-step working

### Step 1: Initially, the bucket contains 5 tokens

When the application starts, assume the bucket is full.

```
        TOKEN BUCKET
     Maximum Capacity = 5

       ┌───────────────┐
       │  ●  ●  ●  ●  ●│
       │               │
       └───────────────┘

       Available: 5 tokens
```

No requests have been processed yet.

### Step 2: Client sends the first request

A client sends a request to the API.

```
       CLIENT
          |
          | Request 1
          v
    ┌───────────────┐
    │ TOKEN BUCKET  │
    │  ●  ●  ●  ●  ●│
    └───────────────┘
```

The rate limiter checks whether a token is available.

- Token available? YES.
- Consume one token.
- Allow the request.

After consuming one token:

```
       ┌───────────────┐
       │  ●  ●  ●  ●  ○│
       └───────────────┘

       Available: 4 tokens
```

`○` represents an empty token slot.

### Step 3: More requests arrive

Suppose four more requests arrive.

Each request consumes one token.

```
Request 1 → Consume 1 token → ALLOWED
Request 2 → Consume 1 token → ALLOWED
Request 3 → Consume 1 token → ALLOWED
Request 4 → Consume 1 token → ALLOWED
```

After all five requests:

```
       ┌───────────────┐
       │  ○  ○  ○  ○  ○│
       └───────────────┘

       Available: 0 tokens
```

The bucket is now empty.

### Step 4: Another request arrives

Now the client sends Request 6.

```
       CLIENT
          |
          | Request 6
          v
    ┌───────────────┐
    │ TOKEN BUCKET  │
    │  ○  ○  ○  ○  ○│
    └───────────────┘
```

The rate limiter checks the bucket.

- Token available? NO.
- Cannot consume a token.
- Reject the request.

HTTP 429 – Too Many Requests

The request is rejected because the bucket has no available tokens.

### Step 5: Tokens are replenished over time

Remember our configuration:

- Refill rate = 1 token.
- Refill interval = 10 seconds.

After 10 seconds, the system generates one token.

```
       BEFORE REFILL

       ┌───────────────┐
       │  ○  ○  ○  ○  ○│
       └───────────────┘
       Available: 0


       AFTER 10 SECONDS

             +1 TOKEN
                |
                v
       ┌───────────────┐
       │  ●  ○  ○  ○  ○│
       └───────────────┘
       Available: 1
```

Now the next request can consume this token and be allowed.

### Step 6: What happens if the bucket is already full?

Suppose the bucket has 5 tokens and the refill timer generates another token.

The bucket cannot contain more than its maximum capacity.

```
Bucket Capacity = 5

Current Tokens = 5

Refill generates +1 token

Result:

Available Tokens = 5 (NOT 6)
```

Extra tokens are discarded.

This ensures that the bucket never exceeds its configured capacity.

## 5. Why Token Bucket allows burst traffic?

This is one of the biggest advantages of Token Bucket.

Suppose:

- Bucket capacity = 5.
- Refill rate = 1 token every 10 seconds.
- Initially, 5 tokens are available.

Now imagine 5 requests arrive simultaneously.

All 5 requests are allowed because the bucket already contains 5 tokens.

```
             5 REQUESTS
                 |
                 v
          ┌─────────────┐
          │ TOKEN BUCKET│
          │ ● ● ● ● ●   │
          └─────────────┘
                 |
          +------+------+ 
          |  |  |  |  |
          v  v  v  v  v
         R1 R2 R3 R4 R5

         ALL REQUESTS ALLOWED
```

This is called Burst Traffic.

The algorithm allows bursts when tokens are available but controls the average rate at which requests can be accepted over time.

## 6. Real-world example: E-commerce application

Imagine your e-commerce application has a Product API.

```
GET /api/products
```

You want to prevent clients from sending too many requests.

You configure:

| Setting         | Value      |
| --------------- | ---------- |
| Bucket capacity | 5          |
| Token refill    | 1 token    |
| Refill interval | 10 seconds |
| Request cost    | 1 token    |

Now:

- A client can immediately send 5 requests.
- The 6th request gets rejected if no token has been replenished.
- After every 10 seconds, one token becomes available.
- The client can send another request.

This helps protect your API from excessive request traffic.

## 7. Advantages and disadvantages

Advantages:

1. Supports burst traffic.
2. Controls the average request rate.
3. Prevents excessive requests from overwhelming an API.
4. Flexible token capacity and refill rate.

Disadvantages:

1. Requires maintaining token state.
2. Requires accurate refill calculations.
3. In a distributed application, shared token state may be needed to enforce one common limit across multiple instances.

## 8. Important interview concepts

| Concept           | Meaning                                                                |
| ----------------- | ---------------------------------------------------------------------- |
| Bucket Capacity   | Maximum number of tokens the bucket can hold.                          |
| Refill Rate       | How frequently new tokens are generated.                               |
| Token Consumption | Every request consumes a token.                                        |
| Burst Traffic     | Multiple requests can be accepted immediately if tokens are available. |
| HTTP 429          | Status code returned when the rate limit is exceeded.                  |

## 9. Pseudocode

```
Initialize:
    BucketCapacity = 5
    AvailableTokens = 5
    RefillRate = 1 token every 10 seconds

When a request arrives:

    Check available tokens

    IF AvailableTokens > 0:

        Consume 1 token

        Allow the request

    ELSE:

        Reject the request

        Return HTTP 429


Token Refill Process:

    Every 10 seconds:

        IF AvailableTokens < BucketCapacity:

            Add 1 token

        ELSE:

            Discard the extra token
```

## 10. Quick revision

Token Bucket – Remember these 5 points

1. Bucket has a fixed maximum capacity.
2. Tokens are generated at a configured refill rate.
3. Every incoming request consumes a token.
4. Requests are allowed when tokens are available.
5. Requests are rejected when no tokens are available.
